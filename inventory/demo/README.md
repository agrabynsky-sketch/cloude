# Демо-данные и нагрузочный тест

Проверка архитектуры `search_daily` на объёме, близком к боевому.

## Масштаб

- **1000 отелей** × 5 room × 3 rate_plan = **15 000 тарифов**
- 3 варианта размещения (1 взр / 2 взр / 2 взр + реб)
- **365 дней** горизонта
- Итого в `search_daily`: **16 425 000 строк** (~1.77 ГБ данных + ~1.78 ГБ индексов)

## Файлы

| Файл | Что делает |
|------|-----------|
| `10_demo_seed.sql` | Гео, 1000 отелей, 5000 room, 15000 rate_plans (sequence-движок) |
| `11_fill_search_daily.sql` | Заполняет `search_daily` на год (чанки по 30 дней) |
| `12_benchmarks.sql` | 3 поисковых запроса (чистый вид, для чтения) |

## Как воспроизвести (MySQL 5.7+ / MariaDB 10.x)

```bash
mysql DB < ../database/01_schema_core.sql
mysql DB < ../database/02_schema_search_cache.sql
mysql DB < 10_demo_seed.sql          # ~0.3 с
mysql DB < 11_fill_search_daily.sql  # ~3.5 мин (16.4M строк)
mysql DB -e "ANALYZE TABLE search_daily;"
mysql DB < 12_benchmarks.sql
```

> `seq_A_to_B` — sequence-движок MariaDB. На MySQL заменить генерацию
> строк на таблицу-справочник чисел или рекурсивный CTE (8.0+).

## Результаты (MariaDB 10.11, warm cache)

| # | Запрос | Строк на выходе | Время |
|---|--------|-----------------|-------|
| Q1 | Поиск по **200 отелям** → min цена/отель | 200 отелей | **~12 мс** |
| Q2 | Поиск **по городу** (city_id) → min цена/отель | 10 отелей | **~1.3 мс** |
| Q3 | **Один отель**, все румрейты, сырая цена | 15 румрейтов | **~0.3 мс** |

Параметры теста: 2 взрослых (occ=200), заезд 2026-07-10, выезд 2026-07-13
(3 ночи), канал web, публичный поиск.

## Что показал тест (и что было исправлено)

1. **Порядок колонок в индексе — критичен.** Исходно индекс был
   `(occupancy_id, stay_date, hotel_id/city_id, …)`. Диапазон по `stay_date`
   «обрывает» индекс: всё, что стоит после него, для отсева не используется.
   Поэтому фильтр по отелю/городу становился остаточным:
   - Q3 (один отель) сканировал **360k строк + row-lookups** → **~1000 мс**.
   - Q2 (город) сканировал 91k строк → ~100 мс.

   **Фикс:** локация ПЕРЕД датой — `(occupancy_id, hotel_id, stay_date, …)`
   и `(occupancy_id, city_id, stay_date, …)`, обе покрывающие. После этого:
   - Q3: **~0.3 мс** (ускорение ×3000)
   - Q2: **~1.3 мс** (×75)

2. **Глобальный ключ размещения.** `search_daily.occupancy_id` = `adults*100
   + children` (одинаков во всех отелях), а не per-room `occupancy_options.id`
   — иначе один `:occ` не фильтрует несколько отелей.

3. **Список отелей — литеральным `IN (…)`,** не `IN (SELECT …)`: подзапрос
   заставляет оптимизатор материализовать и сканировать слой (12 мс против
   190 мс на 200 отелях).

Все три исправления внесены в `database/02_schema_search_cache.sql` и
`database/03_rebuild_and_search.sql`.
