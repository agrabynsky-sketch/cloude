# Unit.Travel — поисковый слой на ClickHouse

Поисковый кэш для инвентори-системы отелей Unit.Travel (PHP 5 + ZF1 + MySQL 5.7).
MySQL остаётся источником истины; в ClickHouse лежат готовые данные для поиска, которые читаются без JOIN.

Кэш отвечает на два запроса:

1. **Выдача по направлению** — минимальная цена за проживание по 500–1000 отелям для дат заезда/выезда и состава гостей.
2. **Карточка отеля** — все доступные рум-рейты выбранного отеля на эти даты и состав гостей, с ценами по ночам.

Состав гостей — по номерам: взрослые + возраста детей, до 4 номеров в запросе. Цена номера — за число гостей (окно цен по числу гостей; нет настроек — одна цена за номер), дети — по детской политике отеля от цены номера и не дороже, чем взрослые (правило отель или категория номера может выключить). Вместимость — только существующие места; доп. кровати и детские кроватки — условия проживания, в расчёт не входят. Правила — раздел 5.

Всё в этой папке проверено на PHP 5.6.40 + Zend Framework 1.12.20 + MySQL 5.7.44 + ClickHouse 24.8 (результаты — в разделе «Проверка»).

```mermaid
    A --> Q
    W["CLI-воркер PHP<br/>scripts/search-sync.php worker<br/>(cron раз в минуту)"] -- claim --> Q
    W -- "читает отель целиком" --> T
    W -- "HTTP INSERT (TSV, gzip)" --> CH[("ClickHouse<br/>unit_search.hotels_search_stay")]
    F["clickhouse/full_load.sh<br/>(ночью, опционально)"] -. "mysql() + named collection<br/>→ hotels_search_stay_new → EXCHANGE" .-> CH
    S["Сайт / API<br/>Search_Model_Stay"] -- "HTTP 8123 (curl)<br/>или MySQL-протокол 9004 (Zend_Db)" --> CH
```

**Главная идея — нарастающие суммы.** Одна строка `hotels_search_stay` = один рум-рейт на одну дату горизонта `[сегодня; сегодня + 365]`.
В строке хранится `c{g}(d)` — сумма цен номера за `g` гостей по продаваемым ночам *до* даты `d`, и `k(d)` — сколько таких ночей было до `d`. Тогда для проживания `[checkin; checkout)`:

* цена = `c{g}(checkout) − c{g}(checkin)`;
* все ночи продаются ⇔ `k(checkout) − k(checkin) = nights`;
* ночь, где на g гостей не продаётся (дневная цена 0), добавляет к `c{g}` 2^40 — разность `≥ 2^40` значит «на g гостей это проживание не продаётся».

Так же хранится число ночей, где свободно не меньше 2 / 3 / 4 номеров (`k2..k4`). Всё, что зависит от даты и тарифа (цены по числу гостей, дневные цены, наследование производного тарифа), считает сборщик; цену детей поиск считает из цены номера за проживание и детской политики отеля (статические колонки строки).

Поэтому поиск читает **2 строки на рум-рейт при любой длине проживания**, а ограничения (CTA, min/max LOS, min/max ADV) берутся из строки даты заезда, CTD — из строки даты выезда.

## 4. Правила расчёта (что считается «доступно» и «сколько стоит»)

Одни и те же правила реализованы трижды — в `Search_Sync_Builder` (PHP), в `clickhouse/03b_build_chunk.sql` (SQL) и в эталоне `tests/reference.php`, и все три дают одинаковый результат.

* **В поиск попадает рум-рейт**, если активны отель, номер и тариф (`active = 1`) и есть связь в `hotels_rates_rooms`.
* **Базовая цена ночи** (цена в календаре, она за `base_occupancy` гостей):
  * самостоятельный тариф — строка `hotels_rates_prices` с `active = 1` и `price IS NOT NULL`, иначе ночь не продаётся;
  * производный тариф (`id_parent > 0`): своя строка с `active = 0` → не продаётся; своя `price` при `derive_type = 0` → своя цена («фиксированная сумма»);
    иначе цена родителя на том же номере × `(100 + dv) / 100`, где `dv` = своя `derive_value` при `derive_type = 4`, иначе `−hotels_rates.derive_value` (изменение производного тарифа — только в процентах).
* **Наличие:** строка `hotels_rooms_availability`, иначе `allotment` номера, `net_booked = 0`, `active = 1`; продаётся, если `active = 1` и `allotment − net_booked > 0`.
* **Цена номера за g гостей** (дети считаются отдельно, раздел 5); `hotels_rooms.pricing_model` не используется:
  * дневная цена `hotels_rates_occupancy_daily(rate_room, g, дата)` с `price > 0` — цена этой ночи (действует, только если ночь продаётся и g не выключено); `price = 0` — **на g гостей в эту ночь не продаётся**, значит и всё проживание с этой ночью на g гостей не продаётся (на другое число гостей — продаётся);
  * иначе строка окна `hotels_rates_occupancy(rate_room, g)`: `amount_type = 0` → база × (1 + amount/100), `1` → база + amount (не меньше 0); `active = 0` → на g гостей не продаётся; нет строки → база (одна цена для любого числа гостей);
  * производный тариф: своя дневная цена > своя строка окна (от своей базы) > как у родителя — цена родителя за g (его дневная цена или его строка окна от его базы) × `(100 + dv) / 100`; в ночь со своей ценой — строка окна родителя к своей цене. Дневная цена 0 у родителя закрывает g и у производного, если у него нет своей дневной цены или своей строки окна на это g.
* **На сколько гостей продаётся** (`gmask`): g ≤ `max_adults` (0 → max(`max_occupancy`, `base_occupancy`)), g ≤ `max_occupancy`, g ≤ 8 и g не выключено (своя строка окна, у производного без своей строки — строка родителя).
* **Дубли строк** (в MySQL нет UNIQUE-ключей, дубли создаёт, например, ошибка пагинации bulk edit): для цены, наличия, надбавки и дневной цены берётся строка с **максимальным id**, целиком. Лучше закрыть дубли ключами из `mysql/00_recommended_indexes.sql`.
* **Ограничения** даты берутся из своей строки цены рум-рейта, иначе из тарифа: `min_los`/`min_adv` (NULL → значение тарифа), `max_los`/`max_adv` (0 или NULL → без ограничения), `cta`/`ctd`. Проверяются по дате заезда (CTA, LOS, ADV) и дате выезда (CTD).
* **Округление** целочисленное half up в копейках — PHP и ClickHouse дают одинаковые суммы до копейки.
* Все цены — в валюте отеля (`id_currency`); поиск сортирует по цене внутри одной валюты.

**Нужно подтвердить с бизнесом** (реализовано так, как показано выше, меняется в одном месте каждой реализации):
1. Производный тариф наследует у родителя цену и цены по числу гостей, но не ограничения (CTA/CTD/LOS) — ограничения только свои или тарифа. Детская политика одна на отель.
2. `min_los` проверяется по дню заезда (как у Booking.com «arrival-based»). Если нужна проверка по каждой ночи — нарастающие суммы это не покрывают, нужна отдельная доработка.
3. Нет строки окна на g гостей → базовая цена; строка с `active = 0` → на g гостей не продаётся.
4. Вместимость, дети и цены по числу гостей — по решениям из раздела 5 (подтверждены).
5. Разные валюты: для сортировки выдачи по цене между странами нужен курс (удобно словарём ClickHouse `dictGet`).
6. `hotels_rates_occupancy_daily`: дневная цена — абсолютная цена ночи на g гостей и заменяет строку окна, `price = 0` — на g гостей в эту ночь не продаётся (решение подтверждено); производный тариф наследует дневные цены родителя (× изменение тарифа), если у него нет своей строки на это g; ночь, закрытая по базовой цене, дневной ценой не открывается. Если таблица на самом деле хранит что-то другое (например, заранее посчитанные цены по всем датам или процент, как было в старой колонке `amount`), правило меняется в `Search_Sync_Builder`, `03b_build_chunk.sql` и `tests/reference.php`.

## 5. Вместимость, дети и несколько номеров

### Правила (решения бизнеса)

1. **Вместимость — только существующие спальные места**, как у Booking.com: `max_occupancy`, `max_adults`, `max_children` и новый `max_infants`. Доп. кровати и детские кроватки (`extra_beds`, `cots`, «и / или» — `cots_and_extra_beds`) вместимость **не увеличивают** и в цену **не входят**: это условия проживания (их цены выводятся примечанием, без настройки — по запросу с подтверждением отеля). Карточка отеля отдаёт эти три поля для условий.
2. **Цена номера — за число гостей** из окна «цены для другого числа гостей» (`hotels_rates_occupancy`): к цене в календаре (она за `base_occupancy` гостей) — процент или сумма за ночь (`amount_type`), «выключено» (`active = 0`) — на столько гостей не продаётся; дневная цена `hotels_rates_occupancy_daily` важнее строки окна, дневная цена 0 — на столько гостей в эту ночь не продаётся. Нет строк — **одна цена за номер для любого числа взрослых** в пределах `max_adults` (бывший per room). Доплата за взрослого сверх `base_occupancy` (бывшая `extra_bed_adult_price`) в поиск не входит — она в условиях проживания. `hotels_rooms.pricing_model` поиском не используется: модель следует из того, настроены ли цены по числу гостей.
3. **Базовое размещение рум-рейта** — `hotels_rates_rooms.base_occupancy`, NULL — как у номера; у производного тарифа — как у родителя (только чтение). Это смысл цены в календаре; в расчёт поиска напрямую не входит (строки окна заданы относительно неё).
4. **Производный тариф наследует цены по числу гостей родителя**: своя дневная цена > своя строка окна (процент или сумма к цене производного тарифа, как в окне родителя) > цена родителя за это число гостей × (100 + %) / 100. Выключенное у родителя число гостей выключено и у производного, если у него нет своей строки. Своя цена ночи в календаре (`derive_type = 0` — «фиксированная сумма») — база производного, к ней применяется строка окна родителя, дневные цены родителя в эту ночь не действуют.
5. **Детская политика — одна на отель** (`hotels_children_groups`, экран «Children's prices by age»): до 4 возрастных групп на 0–17 лет, у группы одна цена за ребёнка за ночь: бесплатно / фикс / % тарифа на номер / % цены взрослого (цена номера / число гостей × %) / полная цена взрослого. Возраст вне групп — взрослый (и для цены, и для вместимости). Отель не принимает детей (`allow_children = 0`) или ребёнок младше `children_min_age` — номер не подходит. Группы по тарифам и календарные исключения цен — следующий этап.
6. **Младенец** — 0–2 года (0–2,99; `Search_Occupancy::INFANT_AGE_MAX`) в детской группе: младенцев не больше `max_infants`; при `is_without_infants = 1` младенец не считается в `max_children` / `max_occupancy` и не занимает место; платит по своей группе (обычно бесплатно).
7. **За сколько гостей цена номера**: за число взрослых; если на столько рум-рейт не продаётся (например, «1 guest» выключен), — за ближайшее большее продаваемое число, а свободные места бесплатно занимают самые дорогие дети. Детей не хватает — номер не подходит.
8. **Не дороже, чем взрослым**: итог номера не больше цены номера за (гостей + платящих детей), если на столько продаётся. В номере с одной ценой для любого числа гостей ребёнок поэтому бесплатен, пока взрослые + дети укладываются в `max_adults`; вернуть контроль отелю — строка окна «3 гостя: + сумма» или реальный `max_adults`.
   **Правило можно выключить**: `hotels.children_as_adults = 0` — для всего отеля, `hotels_rooms.children_as_adults` — для категории номера (NULL — как у отеля, 0 / 1 — своё). Выключено — дети всегда платят по детской политике, даже если цена за столько же взрослых ниже. Свободные места цены номера (пункт 7) дети занимают бесплатно и при выключенном правиле: это не цена взрослого, а места, уже оплаченные в цене номера.
9. **Несколько номеров** в одном запросе (до 4, например «2 + ребёнок 5 лет» и «2»): каждый номер считается отдельно, цена отеля — самая дешёвая комбинация с учётом того, сколько номеров каждого типа свободно (наличие у типа номера общее для всех его тарифов).

Детская цена считается от цены номера **за всё проживание**, округление half up один раз (а не по ночам).

### Расчёт одного номера

```
a  = взрослые + дети, чей возраст не попал ни в одну группу;  a <= 8
дети с местом: все из групп, кроме младенцев при is_without_infants
лимиты: детей с местом <= max_children,  a + они <= max_occupancy,  младенцев <= max_infants
g  = a, если рум-рейт продаётся на a гостей во все ночи проживания; иначе ближайшее продаваемое g из (a; a + детей с местом]; нет — не подходит
P  = цена номера за g гостей за проживание (разность нарастающих сумм c{g})
ребёнок: 1 → 0,  2 → фикс × ночей,  3 → P × %,  4 → P / g × %,  5 → P / g       (half up)
(g − a) самых дорогих детей с местом — бесплатно (заняли места, которые уже в цене номера)
итог = P + цены детей;  если children_as_adults = 1 и на g + платящих продаётся: итог = min(итог, цена номера за g + платящих)
```

Примеры (`tests/occupancy_unit.php` проверяет первые два):

* Номер с одной ценой 1 400 грн за ночь, группа 12–17 — 50 % цены взрослого, 2 взрослых + 12 лет. `max_adults = 3`: 1 400 / 2 × 50 % = 350, но как три взрослых — 1 400, итог **1 400**. `max_adults = 2`: итог **1 750**.
* «1 guest» выключен, 2 гостя — 100 €, 3 гостя — 115 €, 1 взрослый + дети 7 и 9 лет (50 % цены взрослого): цена за 2 гостей, один ребёнок на втором месте бесплатно, второй 100 / 2 × 50 % = 25 €, 125 € → как три взрослых **115 €**.
* То же с выключенным правилом (`children_as_adults = 0`): **125 €**; номер с одной ценой 1 400 грн, `max_adults = 3`, 2 взрослых + 12 лет: **1 750** вместо 1 400.
* Производный тариф −10 %: родитель 94 € за 2 гостей, 108,10 € за 3 (+15 %) → 84,60 € и 97,29 €. Своя строка производного «3 гостя: +20 €» → 104,60 €.

Правило реализовано трижды и сверяется тестами: `Search_Occupancy::price()` (карточка отеля, перерасчёт брони), SQL в `Search_Model_Stay::_roomPricesSql()` (выдача) и эталон `tests/reference.php` (полный перебор детей на свободные места по данным MySQL).

### Кэш ClickHouse

Колонки `hotels_search_stay` (`clickhouse/01_schema.sql`, для существующей таблицы — `01b_upgrade_occupancy.sql`):

* статические: `base_occupancy`, `max_children`, `max_occupancy`, `max_infants` (255 = без лимита), `infants_excluded`, `children_min_age` (255 = отель не принимает детей), `age_group Array(UInt8)` — 18 элементов, возраст 0..17 → номер группы (0 = взрослый), `child_type` / `child_value` — тип цены группы и значение (фикс — копейки за ночь, процент — базисные пункты), `children_as_adults` — правило «не дороже, чем взрослым» (значение номера, NULL → отеля), `extra_beds`, `cots`, `cots_and_extra_beds` — для условий проживания;
* нарастающие: `c1..c8` — цена номера за g гостей (ночь, закрытая на g гостей дневной ценой 0, добавляет 2^40 = `Search_Occupancy::CLOSED`), `k`, `k2..k4` — ночей, где свободно не меньше 1 / 2 / 3 / 4 номеров. Детских нарастающих сумм больше нет: цену ребёнка поиск считает из цены номера за проживание;
* `gmask` — на сколько гостей продаётся (в нём `max_adults`, `max_occupancy`, выключенные строки окна), `max_guests` — максимум.

Объём: 10,25 млн строк = **312 МиБ** на диске (1,64 ГиБ без сжатия). В прошлой версии с детскими нарастающими суммами было 455 МБ, до поддержки детей — 272 МБ.

### Поиск

```php
// один номер: 2 взрослых + дети 7 и 4 лет
Search_Model_Stay::getInstance()->search(array('checkin' => '2026-12-10', 'nights' => 7, 'id_region' => 243836,
    'adults' => 2, 'children' => array(7, 4)));
// несколько номеров
Search_Model_Stay::getInstance()->search(array('checkin' => '2026-12-10', 'nights' => 7, 'id_region' => 243836,
    'rooms' => array(array('adults' => 2, 'children' => array(5)), array('adults' => 2))));
// 'guests' => 2 работает как раньше: 2 взрослых без детей
```

* **Один номер** — всё в ClickHouse: разности нарастающих сумм по двум строкам рум-рейта, затем дети запроса разворачиваются в строки (`ARRAY JOIN` списка детей) и по каждому рум-рейту считаются состав, число гостей цены, цены детей и итог, затем минимум по отелю, сортировка и страница. SQL одинакового размера при любом числе детей.
* **Почему SQL такой**: ClickHouse при разборе запроса раскрывает алиасы, и цепочка «итог → цены детей → цена номера → число гостей» разбиралась 0,5 с. Поэтому промежуточные значения передаются параметрами вложенных лямбд (`arrayMap((gd, ...) -> ..., [значение], ...)[1]` — аналог `let`), разбор занимает ~50 мс.
* **Несколько номеров** — ClickHouse отдаёт по каждому отелю лучший рум-рейт каждого типа номера для каждого номера запроса и сколько номеров этого типа свободно на все ночи (до 4, по `k2..k4`); PHP (`Search_Occupancy::cheapestCombination()`) выбирает самую дешёвую комбинацию, затем фильтр цены, сортировку и страницу.
* Ответ `search()`: у каждого отеля `price` / `price_minor` — за все номера, `rooms` — выбранный рум-рейт и цена каждого номера; для одного номера поля рум-рейта продублированы в самом элементе, как раньше.
* **Карточка отеля** — `hotelRooms($idHotel, $criteria)`: для каждого номера запроса все доступные рум-рейты с разбивкой (`price_adults` — цена номера, `price_children`, `adults` с учётом детей-«взрослых», `guests` — за сколько гостей взята цена номера, `capped` — дети посчитаны как взрослые, по каждому ребёнку группа, место `bed` / `free` (бесплатно на месте, которое уже в цене) / `none` (младенец без места) / `adult` (возраст вне групп), цена и `as_adult`, цены номера по ночам, условия `extra_beds` / `cots` / `cots_and_extra_beds`, `base_occupancy`) и `best` — самая дешёвая комбинация. `hotelRates()` — то же для одного номера (список, как раньше).
* Фильтр `price_min` / `price_max` — по цене отеля (за все номера, после выбора лучшего варианта).

Разбор дороже прошлой версии, потому что цена ребёнка теперь зависит от числа гостей, за которое взята цена номера, и считается в запросе: в первом варианте с цепочкой алиасов разбор занимал 0,5 с, со связыванием через параметры лямбд — ~50 мс на уровень детей. Что пробовали и не взяли: итог в одном уровне с группировкой рум-рейта (разбор 240 мс), отдельный уровень подзапроса (+50 мс), ClickHouse 25.8 (в 2 раза медленнее на этом запросе). Что даёт выигрыш на проде:

* выделенный сервер ClickHouse (здесь 4 общих vCPU): время почти линейно зависит от частоты ядра;
* кэш результатов ClickHouse для выдачи: `Search_Model_Stay::getInstance()->setQueryCacheTtl(60)` добавляет к запросу `SETTINGS use_query_cache = 1, query_cache_ttl = 60` — одинаковый запрос в течение минуты отдаётся за 5–9 мс (проверено через HTTP и 9004 с детьми, ответы совпадают); цены в выдаче могут отставать на эти секунды, бронирование всё равно перепроверяется в MySQL;
* запрос только взрослых (самый частый) по скорости как прежний: для него строится прежний по форме SQL.

## 6. Синхронизация MySQL → ClickHouse через HTTP (текущий этап)

### Как устроено

1. **Очередь** `hotels_search_sync_queue` — одна строка на «грязный» отель. `Search_Sync_Queue::push($hotelId, 'reason')` идемпотентен: повторный вызов только увеличивает `version`.
2. **Воркер** (`Search_Sync_Worker::run()`, запускается `scripts/search-sync.php worker`) атомарно забирает пачку отелей (`UPDATE ... SET claimed_by = token ... LIMIT n`), пересобирает их **целиком** и удаляет из очереди только если `version` не изменилась за время сборки — изменение, пришедшее во время сборки, не теряется. Упавший воркер: через 10 минут отели заберёт следующий.
3. **Сборщик** (`Search_Sync_Builder::build()`) читает отели пачками по 10 (7 запросов на пачку, без JOIN по истории), считает строки по правилам из разделов 4 и 5 и отдаёт их готовыми TSV-строками — память PHP не растёт.
4. **Вставка**: `Search_ClickHouse_Client::insertTsv()` → `POST /?query=INSERT ... FORMAT TabSeparated`, тело сжато gzip, ~250 тыс. строк (≈50 отелей) на одну вставку. Одна вставка = один атомарный блок, поэтому отель никогда не виден наполовину.
5. **Версии**: все строки отеля в одной сборке получают один `ver`; `ReplacingMergeTree(ver, is_deleted)` оставляет последнюю версию, `SELECT ... FINAL` видит только её. Поиск дополнительно требует `min(ver) = max(ver)` для строк заезда и выезда.
6. **Удаления**: рум-рейты, которые были в ClickHouse, но больше не собираются (выключен тариф/номер/отель, удалена связь), получают tombstone-строки `is_deleted = 1`.

## 7. Прямая связь MySQL ↔ ClickHouse без HTTP

**Чтение сайтом через MySQL-протокол ClickHouse (порт 9004)** — то, что по ссылке из документации. ClickHouse принимает подключения как MySQL-сервер, поэтому работает штатный `Zend_Db_Adapter_Pdo_Mysql`:

```php
Search_ClickHouse_Client::setDefault(Search_ClickHouse_Client::factory(array(
    'transport' => 'mysql', 'host' => 'clickhouse.internal', 'port' => 9004,
    'username' => 'search_reader', 'password' => '...', 'dbname' => 'unit_search',
)));
// или сырой Zend_Db:
$ch = Zend_Db::factory('Pdo_Mysql', array('host' => 'clickhouse.internal', 'port' => 9004, 'username' => 'search_reader',
    'password' => '...', 'dbname' => 'unit_search', 'charset' => 'utf8'));
$ch->fetchAll('SELECT id_hotel, count() FROM hotels_search_stay WHERE d = ? GROUP BY id_hotel', array('2026-12-10'));
```

Проверено: `fetchAll/fetchCol/fetchOne`, bind-параметры (PDO эмулирует prepared statements), `quoteInto` с массивами; ответы моделей через 9004 и через HTTP совпадают полностью, скорость одинаковая. Пользователь должен быть создан с `double_sha1_password` (см. `02_users.sql`). Ограничение: нет `INSERT ... FORMAT`, поэтому массовую запись воркера лучше оставить на HTTP.

**ClickHouse сам читает MySQL** (используется в `full_load.sh`):

* табличная функция `mysql(unit_mysql, table = 'hotels')` с named collection из `config.d/unit_mysql.xml` — пароль не хранится в SQL; нужны `SET mysql_datatypes_support_level = 'decimal'` (иначе DECIMAL придёт строкой) и права `MYSQL`, `NAMED COLLECTION`;
* тот же доступ можно оформить таблицей `ENGINE = MySQL(...)` или словарём с источником MySQL (`SOURCE(MYSQL(...)) LIFETIME(300)`) — удобно для справочников (валюты, курсы, типы питания);
* инкрементально так тоже можно (ClickHouse читает `hotels_search_sync_queue` и пересобирает отели SQL-ом), но логика очереди проще и прозрачнее в PHP — рекомендуем: инкрементально PHP-воркер, ночью или при сбоях — `full_load.sh`.

**Потоковая репликация (на будущее):** `MaterializedMySQL` в ClickHouse экспериментальный — для продакшена не рекомендуем. Если понадобится CDC — Debezium/Maxwell (binlog) → Kafka → ClickHouse (Kafka engine) или Altinity Sink Connector; но пересчёт нарастающих сумм всё равно нужен на уровне отеля, поэтому очередь «грязных» отелей остаётся.

```php
// календарь доступности отеля: сколько рум-рейтов продаётся в каждую ночь и сколько номеров свободно
class Search_Model_HotelAvailability extends Search_Model_Abstract {
    public function byDay($hotelId, $from, $to) {
        return $this->_client->fetchAll('SELECT s.d AS d, countIf(s.avail > 0) AS sellable_rate_rooms,
                max(s.avail) AS max_rooms_left
            FROM hotels_search_stay AS s FINAL
            WHERE s.d IN (' . $this->_dateList($from, $to) . ') AND s.id_hotel = ' . $this->_int($hotelId) . '
            GROUP BY s.d ORDER BY s.d');
    }
}
```

Цена одной ночи — это разность нарастающих сумм соседних дат (`c{g}(d + 1) − c{g}(d)`), поэтому для цен используйте
`search()`/`hotelRooms()`/`hotelRates()` или ту же разность, а не сами колонки `c1..c8`.

Правила для своих запросов: всегда `FINAL`; фильтр по `d` первым (ключ сортировки `(d, id_hotel, id_rate_room)`), для диапазона дат одного отеля — явный список `d IN (...)`; в `WHERE` квалифицировать колонки алиасом таблицы, если в `SELECT` есть алиасы с теми же именами; в SQL подставлять только `_int()`, `_intList()`, `_date()`, `_dateList()`. Перед бронированием цену и наличие **обязательно** перепроверять в MySQL: кэш отстаёт на секунды.

Пример JSON API — `application/controllers/SearchController.php` (`/search/hotels?id_region=…`, `/search/hotel?id_hotel=…`): 400 на неверные параметры, 503 без подробностей, если ClickHouse недоступен.

## 10. Эксплуатация

* **OPTIMIZE.** Пока у строк есть несклеенные старые версии, `FINAL` сливает их на лету: на тех же данных поиск шёл 34–43 мс вместо 17–23 мс. Фоновые слияния ClickHouse постепенно это делают сами; `optimize` (≈5 с на 10 млн строк) раз в 1–3 часа и в конце `full_load.sh` держит скорость стабильной.
* **Часовой пояс.** Горизонт считается от «сегодня» PHP (`timezone` в конфиге) и ClickHouse (`today()` в `full_load.sh`) — они должны совпадать. Часы серверов синхронизировать (NTP): `ver` — это время сборки.
* **Мониторинг:** `php scripts/search-sync.php stats` — длина очереди, самый старый элемент, ошибки (`last_error`); алерт, если `oldest` старше 5 минут.
* **Безопасность:** сайт ходит в ClickHouse только пользователем `search_reader` (`readonly`, лимит 3 с на запрос); `search_writer` — только для CLI. Модели не подставляют в SQL ничего, кроме приведённых к int значений и проверенных дат.
* **Горизонт** — 365 ночей (`Search_Sync_Builder::HORIZON_DAYS`), до 8 взрослых в номере (`MAX_GUESTS`), до 4 номеров в запросе (`Search_Occupancy::MAX_ROOMS`, колонки `k2..k4`), до 6 детей в номере. Старые даты удаляет `TTL d + 1 DAY`.
